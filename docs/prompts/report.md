# 报告提示词 · 终版

- **当前版本**：v1.0
- **维护**：队员 E（泳道3 AI 工程）
- **调用位置**：`scripts/gen_reports.py`（离线批量预生成）、`app/api/report/[model]` 的 POST（按需生成）
- **落盘位置**：`data/reports/<model_id>.json`
- **模型**：`qwen-plus`（主）；长报告可切 `glm-5.3-flash`（deep，注意它是推理模型，`max_tokens` ≥ 3000）

---

## 一、输入怎么拼（脚本负责，模型只负责判断）

`gen_reports.py` 按下面顺序拼成一条 user 消息，**没有的部分写"暂无数据"，绝不省略不写**（省略会让模型自己编）：

```text
【机型】{brand} {name} {variant}，首发价 {launch_price} 元
【新机现价】{jd 现价} 元（{captured_at} 采集，来源 {source}）
【历史价摘要】近 30 天：最低 {min}、最高 {max}、中位 {median}；当前价处于第 {p} 百分位
【二手样本摘要】共 {n} 条，95新中位价 {m95}、9成新中位价 {m9}、8成新中位价 {m8}
【避坑知识】{命中的 knowledge 条目，每条：标题 + 正文}
【评测摘要】
1. {标题}（{url}）：{摘要 80 字内}
2. ...
```

> 评测摘要必须是**真实抓取或人工整理**的内容，脚本不生成。没有就留空，模型会在 `sources` 里少写几条——这是预期行为，不是 bug。

## 二、提示词正文

**system**：

```text
你是一个冷静、克制的数码产品买手。你的读者是想买二手或降价新机、但不懂行的普通人。
你只依据用户给出的数据做判断，不补充任何外部知识，不编造数据、不编造来源。
只输出一个 JSON 对象，不要 markdown 代码块，不要解释文字。
```

**user**（模板，`{{...}}` 由脚本替换）：

```text
{{上面拼好的输入}}

请据此生成一份购买决策报告，输出这个 JSON：

{
  "verdict": "buy|wait|avoid",
  "verdict_reason": "一句话结论，40 字内，要具体到价格或风险",
  "price_position": "一句话说明当前价在历史里的位置，例如：近30天第32百分位，比中位价低8%",
  "pros": ["优点，每条 20 字内，2-3 条"],
  "cons": ["缺点，每条 20 字内，2-3 条"],
  "pitfalls": ["这台机器最容易踩的坑，每条 25 字内，2-3 条"],
  "sources": [{"title": "来源标题", "url": "来源链接"}]
}

判定规则（按顺序执行，先命中先定）：
1. 命中任一"严重风险"知识条目（进水/大修/扩容/翻新）且二手样本里该机型有对应描述 → verdict = "avoid"。
2. 当前价处于近 30 天第 30 百分位以下，且二手 95新中位价 ≤ 新机现价的 65% → verdict = "buy"。
3. 当前价处于第 70 百分位以上，或近 7 天涨幅 > 5% → verdict = "wait"。
4. 其余情况 → verdict = "wait"，并在 verdict_reason 里说明"等一个更好的价格点"。

硬性约束：
- sources 只能填写输入里出现过的链接，一条都不许自己造。输入里没有链接就输出空数组 []。
- 不要写"根据某某评测"这种没有具体来源的话。
- 数据缺失时不要用行业经验补齐，直接在 verdict_reason 或 cons 里写"数据不足"。
- 所有价格单位是人民币元，不要换算。
```

## 三、输出契约（前端按这个渲染）

```json
{
  "model_id": "iphone-13-128g",
  "verdict": "buy",
  "verdict_reason": "二手95新已到新机价六成，当前价在近30天低位",
  "price_position": "近30天第28百分位，低于中位价 9%",
  "pros": ["A15 性能仍够用三年", "配件与维修生态最全"],
  "cons": ["128G 容量偏小", "电池健康普遍低于 85%"],
  "pitfalls": ["翻新机常换后盖玻璃", "扩容机改 256G 冒充原装"],
  "sources": [
    { "title": "Apple 保修状态查询", "url": "https://checkcoverage.apple.com/" }
  ],
  "generated_at": "2026-11-03T12:00:00+08:00",
  "generator": "qwen-plus"
}
```

**三色徽章对应**：`buy` = 绿（值得买）、`wait` = 黄（等降价）、`avoid` = 红（别买）。

> ⚠️ 给 B（验机/报告页）的约定：`sources` 是**对象数组**（`title` + `url`），不是字符串数组。原因是前端要渲染成可点链接。如果你已经按字符串数组写了，告诉我，我改脚本。

## 四、版本记录

### v1.0（当前）

- 首版。三条硬规则的目的：**让 verdict 可复现**。不写规则的话，同一个机型今天问是 buy、明天问是 wait，答辩现场被追问就解释不清。
- `sources` 只允许来自输入，配合脚本的后置校验（见下）——这是「无编造来源」这条验收的唯一可靠实现方式，靠提示词约束不住。

## 五、脚本侧后置校验（不通过就重试一次，再不过就丢弃）

`gen_reports.py` 在解析完 JSON 后逐项检查：

| 检查 | 不通过怎么办 |
|---|---|
| `verdict` 在 `buy/wait/avoid` 里 | 重试 1 次 |
| `sources[].url` 全部出现在输入文本里 | 删掉伪造的条目；删光了就保留空数组，并在报告里标注 `sources_trimmed: true` |
| `pros/cons/pitfalls` 都是非空数组 | 重试 1 次 |
| `verdict_reason` 长度 ≤ 60 字 | 截断 |

## 六、人工审清单（E 的活，每份报告 30 秒）
